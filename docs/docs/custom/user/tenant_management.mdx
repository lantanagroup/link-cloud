In Link Cloud, the terms "tenant" and "facility" are used interchangeably to refer to healthcare organizations configured within the system. Each tenant/facility is identified by a unique `facilityId` that must be consistent across all services to ensure proper functionality.

# Tenant Service
The Tenant service acts as the primary entry point for configuring organizations within Link Cloud. It maintains core facility configurations and generates events for scheduled measure reporting periods.

## Core Tenant Configuration Elements
- Facility ID (unique identifier used across all services; two modes: NHSN ORG ID (5 digits) or Custom ID (alphanumeric plus hyphens))
- Facility Name
- Creation and Modification dates
- IsDeleted flag (soft delete status)
- Scheduled Tasks
- Monthly Reporting Plans
  - Report Types
  - Reporting Periods
  - Submission Schedules

## Tenant Lifecycle Management

Link Cloud supports soft delete and restore operations for tenants/facilities, allowing administrators to deactivate facilities without permanently removing their data.

### Soft Delete

When a facility is soft deleted:
- The `IsDeleted` flag is set to `true`
- The `ModifyDate` is updated to track when the deletion occurred
- All scheduled jobs for the facility are removed
- The facility is excluded from default queries (unless `includeDeleted=true` is specified)
- Associated reports are also marked as deleted

**API Endpoint:** `DELETE /api/Facility/softDelete/{facilityId}`

### Restore

A soft-deleted facility can be restored:
- The `IsDeleted` flag is set back to `false`
- The `ModifyDate` is updated to track when the restoration occurred
- All scheduled jobs (Monthly, Weekly, Daily) are automatically recreated based on the facility's configuration

**API Endpoint:** `PATCH /api/Facility/restore/{facilityId}`

**Note:** Only facilities that are currently soft-deleted can be restored. Attempting to restore a non-deleted facility will result in an error.

### Hard Delete

For permanent removal of a facility and all its data:

**API Endpoint:** `DELETE /api/Facility/{facilityId}`

**Warning:** Hard delete is irreversible and will permanently remove all facility data.

### Querying Deleted Facilities

When listing or searching facilities, you can include soft-deleted facilities by setting the `includeDeleted` query parameter:

- `GET /api/Facility?includeDeleted=false` (default) - Returns only active facilities
- `GET /api/Facility?includeDeleted=true` - Returns all facilities including soft-deleted ones

A fully functional tenant requires configuration across multiple services. Each service maintains its own tenant-specific configurations using the `facilityId` as the linking identifier.

# Important Notes

1. Creating a tenant configuration in the Tenant service alone does not create a fully functional tenant. Additional configuration in other services is required.
2. The `facilityId` must be consistent across all services to ensure proper system integration and functionality.
3. Each service captures and manages different aspects of a tenant's configuration, working together to provide complete functionality.

# Best Practices

## Configuration Management
- Ensure all required services are properly configured for each tenant
- Maintain consistent `facilityId` usage across services

## Tenant Deletion
- Use soft delete (`DELETE /api/Facility/softDelete/{facilityId}`) when you may need to restore the facility later
- Use hard delete (`DELETE /api/Facility/{facilityId}`) only when you are certain the facility and all its data should be permanently removed
- When restoring a soft-deleted facility, scheduled jobs are automatically recreated; however, verify that cross-service configurations are still valid
- When querying for facilities in administrative interfaces, consider whether to include soft-deleted facilities using the `includeDeleted` parameter
