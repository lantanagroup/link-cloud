Tenant Service



    

        
Produces: Auditable Event Occurred [event], Report Scheduled [event], Generate Report Requested [command], Get Facilities List [query], Get Facility Configuration [query], Get Service Info [query]
Consumes: Get Facilities List [query], Get Facility Configuration [query], Get Service Info [query]

        
Overview 


The Tenant service is where a tenant (facility) is configured in Link Cloud. It stores each facility's configuration and decides when each facility's reports are due. When a reporting period starts, it produces a ReportScheduled Kafka event. That event carries what the rest of Link Cloud needs to begin: the facility, the measures (dQMs) to evaluate, the frequency, and the start and end of the reporting period.


The service schedules reports in one of two ways, controlled by the DMRP:Enabled setting:


    

  • DMRP disabled (classic scheduling). An administrator chooses which measures each facility reports daily, weekly and monthly. The service schedules one job per facility per frequency.
    • 

  • DMRP enabled. The measures each facility reports come from the NHSN Digital Monthly Reporting Plan (DMRP) API. Administrators no longer choose them. A nightly job per timezone refreshes the reporting plans from DMRP and produces the ReportScheduled events. See DMRP Integration.
    • 



Scheduling uses Quartz.NET with a persistent SQL Server job store (the quartz.QRTZ_ tables in the Tenant database) running in clustered mode. Every instance of the service shares the same jobs, and each job fires on only one instance.


The service also produces:


    

  • GenerateReportRequested events, when an administrator requests an ad hoc report or regenerates a report.
    • 

  • AuditableEventOccurred events, when facilities or vendors are created, changed or deleted.
    • 



The Tenant service does not consume any Kafka topics.

What each setting does:


    

  • MeasureConfig__CheckIfMeasureExists: when true, every measure named in a facility's scheduled reports is checked against MeasureEval before the facility is saved. A measure MeasureEval does not know is rejected.
    • 

  • ServiceRegistry__MeasureServiceUrl: where MeasureEval is. Required when CheckIfMeasureExists is true, and also used to verify the dQM on a DMRP measure mapping.
    • 

  • FacilityIdSettings__NumericOnlyFacilityId: when true, a facility id must be 1 to 5 digits. When false, it may contain letters, digits and hyphens.
    • 

  • DMRP__Enabled: turns the DMRP integration on or off. It must match the Admin UI container's LINK_DMRP_ENABLED value. See Turning DMRP on or off.
    • 

  • DMRP__Api__*: how the service reaches the DMRP API. None of these are required to start the service. Without them, the DMRP endpoints still serve the plans already stored, and any call that needs the DMRP API fails with a message naming this section. Provision ClientSecret as a Key Vault reference.
    • 

  • DMRP__Scheduling__NightlyCron: when the nightly DMRP job runs, read in each facility's own timezone. It must fire before local midnight. An invalid expression falls back to the default.
    • 

  • DMRP__Scheduling__Concurrency: how many facilities one nightly run processes at the same time. This limits the burst of DMRP API calls at the end of a month.
    • 

  • DMRP__Scheduling__CatchUpNights: on how many nights at the start of a month the nightly job retries a facility that has no reporting plan for that month. 0 turns catch-up off.
    • 

  • DMRP__Scheduling__ScheduledFireTimeOverride: a testing aid only. When set (for example 2026-09-30T23:59:00), every nightly run behaves as if it fired at that local time, so the month-end process can be tested on any date. Never set this in production. The job logs a warning on every run while it is set.
    • 



Any DMRP__Api__* timeout or DMRP__Scheduling__* value outside its accepted range falls back to its default instead of stopping the service.

Every facility must have a name and a valid IANA timezone (for example America/Chicago). Creating, updating, deleting, soft deleting or restoring a facility also updates its scheduled jobs.


When DMRP is enabled, creating or updating a facility with any measures in scheduledReports returns 400 Bad Request. Send empty daily, weekly and monthly arrays instead; the service fills in the schedule from the facility's reporting plans. Creating a facility also reads its current month's plan from DMRP, and returns 502 Bad Gateway if DMRP cannot be reached. Nothing is saved in that case, so the request can simply be retried.


Soft Delete 


The Tenant service supports soft deletion of facilities. Instead of removing the facility record, a soft delete sets its isDeleted flag to true. The facility's configuration and history are kept, but the facility is no longer active.


When a facility is soft deleted:


    

  • Its classic scheduled jobs are removed, so no new reports are scheduled for it.
    • 

  • The DMRP nightly job skips it, because it only processes active facilities.
    • 

  • Its DMRP reporting plans are kept. They are the record of what the facility was enrolled to report.
    • 



A soft deleted facility can be restored, which recreates its scheduled jobs. A permanent delete, by contrast, also deletes the facility's DMRP reporting plans.


DELETE /api/Facility/softDelete/{facilityId} 


Soft deletes a facility by setting its isDeleted flag to true. Calling it on a facility that is already soft deleted is safe; it removes any jobs left behind.


Parameters:


    

  • facilityId (path, required): The unique identifier of the facility to soft delete.
    • 



Response:


    

  • 204 No Content: The facility was soft deleted.
    • 

  • 400 Bad Request: The request is invalid.
    • 

  • 404 Not Found: No facility exists for the specified facilityId.
    • 

  • 500 Internal Server Error: An error occurred during processing.
    • 



PATCH /api/Facility/restore/{facilityId} 


Restores a soft deleted facility by setting its isDeleted flag back to false, and recreates its scheduled jobs.


Response:


    

  • 204 No Content: The facility was restored.
    • 

  • 400 Bad Request: The request is invalid.
    • 

  • 404 Not Found: No facility exists for the specified facilityId.
    •

Report Scheduling 


Both scheduling methods produce the same ReportScheduled event, so services downstream cannot tell which one produced it. Each event is keyed by facility id and contains:


    

  • ReportTypes: the dQMs to evaluate.
    • 

  • Frequency: Daily, Weekly or Monthly.
    • 

  • StartDate and EndDate: the reporting period, in UTC. Periods are calculated in the facility's own timezone. A day runs from midnight to 23:59:59, a week starts on Sunday, and a month starts on the 1st.
    • 

  • ReportTrackingId: an id for the report, also sent as the X-Correlation-Id header.
    • 



Classic scheduling (DMRP disabled) 


Each facility stores the dQMs it reports in three lists: daily, weekly and monthly. For each list that is not empty, the service creates one Quartz job named {facilityId}-{frequency} in the ReportScheduled job group. Each job fires at the start of its period, in the facility's timezone:






Frequency
Fires






Daily
Every day at midnight




Weekly
Every Sunday at midnight




Monthly
The 1st of every month at midnight






When it fires, the job produces a ReportScheduled event for the period that has just started. Each event gets a new, random ReportTrackingId.


When the service starts, it creates any missing jobs for every active facility. When a facility's lists change, only the jobs for the changed frequencies are replaced.


DMRP scheduling (DMRP enabled) 


When DMRP is enabled, the classic jobs are not used. Instead, there is one nightly job per timezone in use. See The nightly scheduling job for how it works.


DMRP Integration 


What DMRP is 


DMRP (Digital Monthly Reporting Plan) is an NHSN API, developed by Leidos for CDC, that says which NHSN measures a facility is enrolled to report for a given month. With DMRP enabled, the reporting plan in NHSN becomes the source of truth for what each facility reports. Administrators no longer choose a facility's measures by hand.


DMRP is not a separate deployment. It is a module (the DotNet/DMRP project) that runs inside the Tenant service when DMRP:Enabled is true. Its data is stored in the Tenant database, and its endpoints are served by the Tenant service under /api/dmrp. When the flag is false, the module does nothing and the /api/dmrp routes do not exist.


How the DMRP API is called 


The service reads a facility's plan in two steps:


    

  1. It requests a token from DMRP:Api:TokenUrl using the OAuth 2.0 client credentials grant (DMRP:Api:ClientId and DMRP:Api:ClientSecret). The token is cached and reused until shortly before it expires.
    2. 

  2. It calls two operations under DMRP:Api:BaseUrl, one for each NHSN component, passing the token as a bearer token:
    3. 







Operation
Component
Covers






GET /msc?nhsnorgid={facilityId}&year={year}&month={month}
MSC
Medicine reports




GET /ps/annual/mrp?nhsnorgid={facilityId}&year={year}&month={month}
PS
Patient safety






Both components are reported monthly. The word "annual" in the patient safety path is part of the operation's name and does not describe how often it is reported.


The response lists only the measures the facility is enrolled in. DMRP has no way to say "not enrolled"; a measure that is missing from the response is not enrolled.


Measure mappings 


DMRP names NHSN measures (for example HOB). Link evaluates dQMs. A measure mapping connects the two: it says which dQM Link runs for an NHSN measure, and at what frequency (Daily, Weekly or Monthly). Each NHSN measure has at most one mapping, and several measures may map to the same dQM.


Administrators manage mappings through /api/dmrp/measure-mappings. A mapping's dQM is checked against MeasureEval when it is created or updated.


If DMRP returns a measure that has no mapping, the service records a placeholder mapping for it with no dQM. The placeholder appears in the measure mappings list so an administrator can see it and complete it by setting a dQM and a frequency. Until then, that measure schedules nothing. Once it is completed, every facility enrolled in that measure picks it up without any other change.


Facility reporting plans 


The service stores what DMRP says in the FacilityReportingPlans table. There is one row per facility, component, measure and month. Each row records:


    

  • the facility id, component (MSC or PS) and NHSN measure,
    • 

  • the reporting month and year,
    • 

  • the measure mapping it uses, if there is one,
    • 

  • IsReporting: whether the facility is currently enrolled.
    • 



Updating reporting plans from DMRP 


Updating a facility's plan for a month (a "sync") works as follows:


    

  1. Read the facility's plan for the month from both DMRP operations.
    2. 

  2. Match each measure to its measure mapping, creating a placeholder mapping for any measure that has none.
    3. 

  3. Add a row for each enrollment that is new.
    4. 

  4. Set IsReporting back to true on any row DMRP returns again after it had been withdrawn.
    5. 

  5. Set IsReporting to false on any row DMRP no longer returns. The row is kept as history, not deleted.
    6. 



Two safety rules apply:


    

  • If DMRP returns no measures at all for the facility, nothing is changed. An empty answer looks the same as a facility DMRP knows nothing about, so the service does not treat it as a withdrawal from everything.
    • 

  • A withdrawal only applies within a component that returned data. If the patient safety operation returns nothing, the facility's patient safety rows are left alone even while its medicine rows are updated.
    •

The nightly scheduling job 


When DMRP is enabled, report scheduling is done by one Quartz job per timezone in use (the DmrpNightly job group, one job named after each timezone). By default each job runs at 23:59 in its timezone. It reads the facility table at run time, so it always works from current data.


Each run does the following:


    

  1. Work out which periods start at the coming midnight. A Daily period starts every night. A Monthly period also starts when the coming midnight is the 1st of a month. Weekly periods are not produced while DMRP is enabled.
    2. 

  2. Find the active facilities in the timezone. Soft deleted facilities are skipped. Facilities are processed in parallel, up to DMRP:Scheduling:Concurrency at a time.
    3. 

  3. Refresh the plan from DMRP when due, for each facility:

      

    • On the last night of a month, sync the month that is about to start.
      • 

    • On the first CatchUpNights nights of a month (the 1st to the 3rd by default), sync any facility that still has no rows for the month. This repairs a month-end sync that failed, and covers a facility added after the month began. If the catch-up finds an enrollment, the job also produces that month's Monthly event late, so the facility loses a few days of the month instead of the whole month.
      • 

    

    4. 

  4. Build the facility's schedule. The job reads the facility's enrolled measures for the month (IsReporting true), looks up each one's mapping, and groups the dQMs by the mapping's frequency. Measures with no dQM are left out. If a measure maps to Weekly, a warning is logged and it is not scheduled.
    5. 

  5. Produce the events. For each period that starts at midnight and has at least one dQM, the job produces a ReportScheduled event. A facility with nothing to report is skipped.
    6. 



If one facility fails, the error is logged and counted, and the job carries on with the rest.


The ReportTrackingId on these events is not random. It is built from the facility id, the frequency and the period start, so it is always the same for the same report. The Report service rejects a ReportScheduled event whose tracking id it has already stored. As a result, running the job again for the same night (after an outage, a restart part way through, or a manual run) cannot create a duplicate report.


If the service is down when a job should have run, Quartz runs it once when the service comes back, and the job still produces the events for the night that was missed.

The job is kept in step with the facilities automatically:


    

  • When the service starts, it creates a job for every timezone used by an active facility, and removes jobs for timezones no facility uses.
    • 

  • When a facility is created, updated or restored, the service makes sure its timezone has a job.
    • 

  • A change to a facility's reporting plan never changes the Quartz jobs, because the job reads the plans each time it runs.
    • 



The facility's stored scheduledReports field is also filled in from its reporting plan for the current month whenever the facility is saved. This shows what the facility is reporting. The nightly job does not rely on it; it reads the reporting plans directly.


Turning DMRP on or off 


Only one scheduling method runs at a time, and the switch happens when the service starts:


    

  • Turning DMRP on: at startup, the service deletes all classic jobs before it starts the scheduler, so an old job cannot fire with an outdated measure list. It then creates the nightly timezone jobs.
    • 

  • Turning DMRP off: at startup, the service deletes the nightly timezone jobs and goes back to classic scheduling, rebuilding each active facility's classic jobs from its stored scheduledReports.
    • 



DMRP:Enabled on the Tenant service and LINK_DMRP_ENABLED on the Admin UI must have the same value. If the UI is off and the service is on, the facility form asks for a schedule that the service then rejects. If the UI is on and the service is off, the form sends an empty schedule and the facility is created with no reports scheduled, without any error. Never turn the UI on before the service.

Health check 


When DMRP is enabled, the service's /health endpoint includes a DMRP check. It calls the DMRP API's /msc operation with a 5 second timeout. Any answer that shows the API is reachable, including 401, 400 or 404, counts as healthy. If DMRP cannot be reached, the check reports Degraded rather than Unhealthy, because the service can still schedule from the plans it has already stored. If DMRP:Api:BaseUrl is not set, the check is skipped.


Mock DMRP service for local testing 


The real DMRP API can only be reached from the CDC development environment. For local development and Link's lower environments, the repository includes a mock DMRP service, MockDmrpApi (DotNet/MockDmrpApi). It never runs in production.


The mock serves the same two operations the Tenant service calls (GET /msc and GET /ps/annual/mrp) and a token endpoint, so the Tenant service follows exactly the same steps against the mock as it will against the real API. It returns whatever enrollments it has been given, which lets a test set up an exact scenario.

    • 



Running it locally. In the docker-compose stack the service is called mock-dmrp-api and listens on port 6159. The local stack turns DMRP on for the Tenant service and points it at the mock, so no extra setup is needed:


docker compose up -d mock-dmrp-api tenant



To test a facility locally:


    

  1. Enroll the facility in a measure for a month with POST http://localhost:6159/api/mock-dmrp/entries, for example {"facilityId":"100","component":"MSC","measure":"HOB","reportingMonth":10,"reportingYear":2026,"isReporting":"Y"}.
    2. 

  2. Make sure a measure mapping exists for that measure, with a dQM and a frequency of Daily or Monthly, using POST /api/dmrp/measure-mappings on the Tenant service.
    3. 

  3. Create the facility, or call GET /api/dmrp/reporting-plans/facilities/100?refresh=true if it already exists, so the Tenant service reads the plan from the mock.
    4. 

  4. To test the month-end process without waiting for the end of a month:

      

    • Enroll the facility in the mock for the following month as well.
      • 

    • Set DMRP__Scheduling__ScheduledFireTimeOverride on the Tenant service to the last night of the current month (for example 2026-10-31T23:59:00). Each run then behaves as if it were that night: it syncs the next month and produces its Monthly event.
      • 

    • The job still runs at 23:59 by default. To see it sooner, also set DMRP__Scheduling__NightlyCron to run more often, for example every 5 minutes with 0 0/5 * * * ?. Remove both settings when you are done.
      • 

    

    5. 



The mock's settings are under the MockDmrpApi section. MockDmrpApi:Enabled must be true for it to serve anything; when it is false, every route except /health and /api/mock-dmrp/info returns 503. Full details are in DotNet/MockDmrpApi/README.md.


The mock's API contract is a best guess, because the real DMRP API description has not been published yet. Expect changes when it is. The mock's token is also signed differently from the real NHSN token (a shared secret instead of published public keys), so token validation is the one part that the mock cannot fully test.

Signing keys 


Some EHRs (for example Epic) require Link to authenticate by sending a signed JWT to the EHR's /token endpoint. The private keys used to sign these JWTs are not stored in the Tenant service. They are stored as PEM secrets in Azure Key Vault.


A vendor can name the Key Vault secret to use, in its authentication.signingKeySecretId field. The name must be 1 to 127 letters, digits or hyphens. Sending null removes it.


When DataAcquisition needs to authenticate a facility, it chooses the key like this:


    

  1. If the facility's vendor has a signingKeySecretId, it uses that secret. This lets every facility on the same vendor share one key.
    2. 

  2. Otherwise, it uses the secret named {facilityId}-pem.
    3. 



(DataAcquisition's DataSourceAuth:KeySource setting can instead read the key from the facility's authentication configuration in the database. This is a temporary fallback that will be removed.)


Rotating a key:


    

  1. Add the new key to Key Vault as a new secret, and give its public key to the EHR.
    2. 

  2. Update the vendor's signingKeySecretId to the new secret name.
    3. 

  3. Once the new key is working, remove the old secret.
    4. 



The following sequence diagram shows how the key is used when Link authenticates with an EHR:


sequenceDiagram
    participant DA as DataAcquisition
    participant T as Tenant service
    participant KV as Azure Key Vault
    participant E as EHR

    DA->>T: Get facility (with vendor)
    T-->>DA: Vendor signingKeySecretId (if set)
    DA->>KV: Get PEM secret (vendor secret, or {facilityId}-pem)
    KV-->>DA: Private key
    DA->>DA: Create and sign JWT
    DA->>E: POST /token (client assertion JWT)
    E->>E: Verify signature with Link's registered public key
    E-->>DA: Access token
