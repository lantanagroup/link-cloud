# Kafka operations

Link.UI exposes the Kafka console under **Operations → Throughput and scaling → Kafka**.
Admin.BFF owns the broker calls at `/api/ops/kafka`. Link.UI does not open a broker connection.

The console has four panels. Search, filter, sort, and page stay in the query string. Times are the viewer's local time, with UTC on hover. Test groups named `e2e-diag-*` and `Dynamic:*` stay hidden unless the page asks for them.

- **Overview.** Controller, broker count, under-replicated partitions, offline partitions, and ISR shrinks. An offline partition counts as under-replicated. An ISR shrink is an online partition whose leader is still in the ISR and whose ISR is smaller than the replica set. Topics show partitions, replication factor, key class, produce rate, and total lag. When the group read fails, topic lag is shown as unknown rather than zero. Lag is also listed per group. The panel refreshes in place.
- **Topic.** Leaders, replicas, in-sync replicas, topic config, and lag per partition per group. **Add partitions** sits behind an Advanced disclosure. The change is permanent: Kafka does not shrink a topic, and existing keys are remapped. The operator types the topic name, sees the same dry run an approver sees, and submits a reason. The main topic, its retry topic, and its error topic increase together. A retry or error topic that is missing, or that would shrink, refuses the change. When a sibling is behind the main topic, the same disclosure offers **Complete topic family**. That raises only the siblings that exist and are behind, up to the main topic's count. It does not change the main topic, and it does not start the partition-change rate limit. An even family is refused.
- **Consumers.** Group state, members (client id, host, assignment), lag per partition, and total lag. Offsets are read one consumer group at a time. The broker description does not include a time since the last rebalance. The primary actions are add or remove replicas. A replica count above the partition count is idle and is refused. The page then waits until the group is Stable, the member count matches, and every partition is assigned. Scaling to zero members is finished when the group is missing or has no members.
- **Brokers.** State, rack, partition count, leader count. Log-directory size is not available through the client this service uses, so the column says so. Adding a broker waits until it is registered. A follow-up rebalance is a separate request. Decommission is guided: preview the moves, refuse any broker whose `process.roles` contains `controller`, refuse a move that would leave a topic with fewer brokers than its replication factor or `min.insync.replicas`, move replicas off, wait until the broker holds no replicas and no leaders and the cluster has no under-replicated or offline partitions, and only then stop the broker. The id returned as the active controller is not used for that decision. Roles are read one broker at a time. Each broker role read waits 15 seconds. If any broker's roles cannot be read, decommission is refused. A poll that fails is retried with backoff until `KafkaOps:ScaleTimeoutSeconds`. The request then closes as timed out. A timed-out decommission does not stop the broker and does not cancel the reassignment. The environment stays blocked until that reassignment finishes, fails closed, or an approved cancel verifies the original replicas. If the replicas finish moving after the timeout, the request completes and the broker is still not stopped. Cancelling an in-flight decommission or rebalance is its own request: a different person must approve it, the provider cancels that request's reassignment, and the request completes only when the live replicas match the assignment recorded before the move. A cancel that does not restore those replicas fails and leaves the original request open.

`IsLinkAdmin` does not grant these actions.

| Action | Permission |
|---|---|
| Read the four panels, dry runs, and the rights probe | `CanViewInfrastructure` |
| Create a partition increase or a family completion | `CanManageKafkaTopics` |
| Create a replica, broker, or rebalance change | `CanManageScaling` |
| Approve, reject, or cancel | The permission that matches the change: `CanManageKafkaTopics` for a partition increase or a family completion, `CanManageScaling` for a replica, broker, rebalance, or cancel of those moves. The wrong permission is refused with 403. |
| Execute a partition increase or a family completion | `CanManageKafkaTopics` |
| Execute a replica, broker, rebalance, or cancel | `CanManageScaling` |

## Topic migration

Repartitioning by the temp-topic method is a separate operation from **Add partitions**. The operator runbook is [kafka-topic-migration.md](kafka-topic-migration.md). Slice 1 increases only. The recreated topic starts empty, consumer groups are written to offset 0, and the `_linkmig-` backup is kept until a person confirms cleanup or the backup retention expires. The backup is not copied onto the new topic. Use the in-place add when the topic can be quiet and the retained records can stay on their current partitions. Use the migration when the run needs that backup and rollback up to the delete.

`DataAcquisitionRequested` is not hard-blocked. Its producers hash the patient key with murmur2, the same partitioner MeasureEval uses.

An in-place add still remaps keys. The dry run names the keyed producers (workload and source file), the key shape, and the share of keys that move. That share is `1 - N/M`, where N is the current partition count and M is the requested count.

## What the service refuses

The UI displays these rules. Admin.BFF enforces them.

1. The new partition count must be higher than the current count and no higher than `KafkaOps:MaxPartitionsPerTopic` (default 24).
2. The main topic, the retry topic, and the error topic are raised together. None of them can shrink. Retry and error topics are not increased on their own. The exception is a family completion: it raises only a sibling that exists and has fewer partitions than the main topic. A sibling that is already ahead is left as it is. The main topic is never in that list.
3. Execute waits until every member of every subscribed group advertises the expected config version on `client.id` (`<service>-<host>-c<version>`, version 1). An empty group does not block. A member that does not advertise the version does. Consumer clients are unchanged by this console, so a group that still has members refuses an increase until those clients advertise the version.
4. Key class comes from the topic catalog. Unknown topics are treated as facility-keyed. Facility keys are `{facilityId}`, patient keys are `{facilityId}:{patientId}`, and report keys are `{facilityId}:{reportScheduleId}`. Those topics keep per-key order, so an increase waits for a quiet window: zero lag in every subscribed group and no produce traffic for at least twice the metadata refresh, checked again immediately before execute. The dry run for a facility-keyed topic states that one facility can never use more than one partition. Skipping the quiet window needs a second approver and a reason. Log, correlation, and health topics may change while traffic is moving. `DataAcquisitionRequested` is not hard-blocked. Producers hash its key with murmur2, the same partitioner MeasureEval uses.
5. The new partition count is the replica ceiling (`maxReplicas` stays at or below the partition count). The consumers panel shows that ceiling and refuses a scale past it.
6. After the increase, the request stays open until every subscribed group with members has every partition assigned. If that takes longer than three metadata-refresh intervals, the request records a slow-convergence audit.
7. A verification window (default 15 minutes, `KafkaOps:VerificationWindowSeconds`) then checks that lag did not rise above the baseline and that a partition whose high watermark moved also moved its committed offset. The request closes as done or needs attention.
8. One change is in flight per environment. A topic family also waits `KafkaOps:RateLimitMinutes` (default 30) after the main topic's partition count changes. The clock starts at that change, including when the retry or error increase then fails. A refusal before the main topic changes does not start it. A family completion does not read that clock and does not start it. The request being executed is left out of the in-flight check, so approving it does not block its own run. A failed group read refuses the plan. It is not treated as zero lag.
9. While a partition reassignment is in flight, plan, create, approve, and execute are refused for partition increases, family completions, rebalance, decommission, and add-broker. Replica scaling is not refused for that reason. The message names the topics. A cancel of the in-flight reassignment is still allowed. It records the topics still listed as in flight and checks only those partitions against the original replicas. A list line that names a partition is checked exactly. A list that names only topics still checks every partition of those topics. A listed partition that is already on the requested replicas when the cancel is checked counts as already moved. Partitions that already moved keep their new replicas, and the progress says how many and that the broker was not stopped. An unknown list refuses the cancel. A decommission or rebalance that is executing, converging, or timed out counts as in flight, including after its own timeout. The request being executed is left out, so it does not block its own re-plan. The .NET client cannot list reassignments, so the service asks the same provider that executes them. If that answer is missing, times out, or is unsupported, the list is unknown and those same moves are refused with "Cannot confirm no reassignment is in flight." A known-empty list closes a timed-out decommission or rebalance as failed. An unknown list does not finish it and does not stop the broker. The disabled provider does not query the cluster, so its answer stays unknown and those moves are refused. That refusal says to enable an infra provider to allow this. Partition increases are included, so the disabled provider cannot add partitions.

The requester cannot approve their own request when a second approver is required. A partition increase, a decommission, a rebalance, and a cancel of a reassignment always need a different person. A family completion needs a different person when the topic is order-sensitive, when a quiet-window override is set, or when `KafkaOps:RequireSecondApprover` is true. A family completion of a topic that is not order-sensitive can be approved by the requester when that option is false. Replica and add-broker changes need a second approver only when `KafkaOps:RequireSecondApprover` is true. Production is read-only unless `KafkaOps:ReadOnly` is set to false. A missing value means read-only in Production and writable elsewhere.

Pending requests are stored through `ICacheService` for 24 hours. Each request, approval, rejection, execution, failure, timeout, and convergence result is also produced to `AuditableEventOccurred`. The audit producer does not create that topic. If execution is marked and then the broker or the provider refuses the change, the request is stored as failed rather than left executing.

## Broker and replica changes

Describe, the rights probe, and partition increases use one Admin client in Admin.BFF. Replica moves and process scaling go through `IKafkaInfraProvider`.

| Provider | When it runs |
|---|---|
| Disabled | Default. The buttons explain that broker and replica changes stay off until they are enabled. Partition increases are refused too, because this provider cannot confirm that no reassignment is in flight. |
| Strimzi | Patches a KafkaNodePool and a Deployment or scaled object, and submits a KafkaRebalance (`add-brokers` or `remove-brokers`). Each request uses one name, `link-ops-` plus the request id. If that name already exists, the apply is refused. A repeat proposal for the same request sets `strimzi.io/rebalance` to `refresh` instead of creating another resource. The resource is deleted when that decommission or rebalance reaches a terminal state. A cancel request does not own the resource, so rejecting or failing the cancel leaves it in place. Removing a broker sets `strimzi.io/remove-node-ids` to that id and decreases `spec.replicas` by one. It stays inert until the cluster client is configured. In-flight reassignment is every KafkaRebalance that is not Ready or Stopped. Rebalancing, PendingProposal, or ProposalReady counts as in flight even when Ready is also set. A resource with no status yet counts as in flight. |
| LocalCompose | Dev proof only. `docker compose` scale, start, and stop for one named project, and `kafka-reassign-partitions.sh` for the replica plan. The same exec channel lists in-flight work with `--list`. When the move finishes or is cancelled, that script runs again with `--verify` against the request JSON so broker and topic replication throttles are cleared. A missing file is skipped. `No partition reassignments found.` is a clear cluster. A `topic-partition: replicas:` line, or a JSON `topic` field, names the busy topics. A non-zero exit, an empty reply, or text that is neither of those is unknown. `KafkaOps:ComposeFile` is a pipe-separated list of compose files passed with `-f`. The extra-broker profile, the extra-broker service, and the broker service prefix are settings. Refused when the host environment is Production or the project name is empty. This repo has no separate LocalCompose file. Point `KafkaOps:ComposeFile` at the kit file below so the consumer and producer use the same tmpfs mounts. |

The console describes only the catalog's consumer groups. It does not list every group on the cluster. A catalog group that does not exist is shown with no members. Admin calls share one client and one gate, so two native requests do not run at once. Each request sets its own timeout. Confluent.Kafka 2.16.0 (librdkafka 2.16.0) is the client every .NET service uses. Its release notes do not claim a fix for `free(): double free` while freeing a `ListConsumerGroups` result after a broker loss, so the catalog-only describe and the single admin gate stay in place. The client has no `CoordinatorLoadInProgress` code, and this service does not treat that name as a stale signal. Coordinator loss is `NotCoordinatorForGroup` or `GroupCoordinatorNotAvailable`. A stale error on one group or one partition, not only a thrown client error, rebuilds the client. A success on one operation does not clear the failure count of another. The replacement client is built under the gate and the old client is disposed then, without waiting for other callers. The .NET client in 2.16.0 still does not expose `AlterPartitionReassignments`, `ListPartitionReassignments`, or `DescribeLogDirs`. The gateway therefore reports the in-flight reassignment list as unknown, and the service asks the infrastructure provider. An unknown answer refuses the moves in rule 9. When the provider is disabled, that refusal says to enable an infra provider to allow this. Partition increases are refused for the same reason. It is not treated as a clear cluster. Requests this service is already tracking still block the environment. On a local compose or disabled-provider path, a finished rebalance, decommission, or add-broker then runs preferred leader election for the partitions that moved. Unclean election is not used. An election failure is a warning on the request and does not fail it. Strimzi skips that call because the platform moves leadership. The local provider applies the replica plan by running `kafka-reassign-partitions.sh` inside the broker container. Emptiness is the topic metadata: no replicas and no leaders on that broker, and no under-replicated or offline partitions. Log-directory bytes stay unknown. A throttle is optional (`KafkaOps:ReassignmentThrottleBytesPerSecond`).

`GET /api/ops/kafka/capabilities` is the rights probe. For each catalog topic it reports `DescribeTopics` with authorized operations and a validate-only `CreatePartitions`. A successful probe is cached for `KafkaOps:CacheSeconds`. A failed probe is not cached. Run that probe in each deployed environment before the first real increase. This runbook does not call a deployed host. Proceed only when the probe shows the principal can alter partitions, the topic operator is not reconciling those topics back down, and the replication factor is acceptable. The console lists catalog topics. Broker-internal topics are not operated from this page. Unknown names remain facility-keyed in the planner.

## Local proof

Use a broker you can destroy. Do not point this kit at a shared cluster.

The kit is `Scripts/kafka-ops-proof/`. `compose.yml` is a three-broker KRaft cluster plus a fourth broker on the `extra-broker` profile, a producer, and a consumer service named `consumer` in group `ops-proof-consumers` on topic `ops-proof-log`. Each broker listens on PLAINTEXT for the other brokers and on a HOST listener advertised as `localhost` at ports 19094, 19095, 19096, and 19097. The compose file publishes no host ports and sets no container name. `compose.publish.yml` adds proxies that publish those host ports. It does not change broker 0, so a second start does not recreate the controller. The runner refuses to start unless `KAFKA_PROOF_ALLOW=1`. On the day-to-day workstation it also refuses unless `KAFKA_PROOF_ALLOW_ON_THIS_PC=1`. A refusal exits 2. The producer and the consumer mount `/etc/kafka/secrets`, `/mnt/shared/config`, and `/var/lib/kafka/data` on tmpfs, so scaling those services away does not leave anonymous image volumes. Stopping the project still removes the extra broker and the project volumes.

```
$env:KAFKA_PROOF_ALLOW = '1'
./Scripts/kafka-ops-proof/run-proof.ps1
./Scripts/kafka-ops-proof/run-proof.ps1 -Publish
./Scripts/kafka-ops-proof/run-proof.ps1 -Down
```

The shell equivalent is `run-proof.sh`, `run-proof.sh --publish`, and `run-proof.sh --down`. `-Publish` publishes the HOST listener through the proxies. Broker 0 stays advertised on `localhost:19094`, so `KAFKA_PROOF_PORT` must stay 19094 (never 5280-5294, and never 19095-19097). The runner sets `KAFKA_BOOTSTRAP` to that address. Without that variable the console step is skipped and does not prove the broker path. The runner's own checks do.

The runner:

1. Runs the Kafka unit tests when `dotnet` is on PATH. Those tests are the partition-add guard: an order-sensitive topic with lag is refused, a drained order-sensitive topic is allowed, a log topic does not need the quiet window, and `DataAcquisitionRequested` is eligible. They also cover the replica ceiling, the controller refusal, and the decommission planner. A missing `dotnet` skips this step and says so. It does not say the broker variable is missing.
2. Reads the cluster and requires brokers 0, 1, and 2. `-Publish` passes `--no-recreate` so an existing broker 0 is left in place.
3. Scales the proof consumer to 3 and waits until the group is Stable with 3 members.
4. Starts broker 3 and waits until it is registered.
5. Moves a replica of each `ops-proof-log` partition onto broker 3, moves those replicas back to brokers 0, 1, and 2, checks that broker 3 is empty, and checks that the topic has no under-replicated partitions.
6. While broker 3 is still up, reads each broker's `process.roles` through the real gateway. Brokers 0, 1, and 2 are controller-eligible. Broker 3 can be decommissioned. Broker 0 cannot.
7. Stops broker 3 only after that empty check and the role check.
8. When `KAFKA_BOOTSTRAP` is set, drives the console service: three consumer groups, then a two-person approve and execute that raises `ReadyToAcquire` and its retry and error topics. That step is separate from the unit tests so it does not run before the cluster is up. It runs after broker 3 has stopped.

Screenshots of the four panels can be taken with `LinkUi:KafkaOpsFixture=true` on a local Link.UI process. That flag is not in the committed settings. It serves a recorded Admin.BFF response, including a disabled provider, so the pages render without a broker.
